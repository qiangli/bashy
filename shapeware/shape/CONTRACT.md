# Shape CLI and site MCP Contract (`CONTRACT.md`)

Behavioural specification for the `shape` surface (`bashy shape` plus the site MCP shaping tools). Certified against bashy at commit `bb467707bd5f0f7f269aab4e5ff9c188c7c00d23`. Every rule below is demonstrated by at least one assertion or acceptance line, a rule that names a set defines the set, and assertions run in a fresh HOME with sandbox fakes only.

## How assertions are judged

- Assertions are ordered and run against one fresh HOME; no app is registered in it, so `no-such-app-xyz` is never a registered app. Every `shape` command passes `--user shape-tester` explicitly, so no `BASHY_PRINCIPAL` from the environment is assumed. Run-specific values are replaced with placeholders (`{ID}`, `{PORT}`, `{TIME}`, `{KEY}`) where they occur.
- Only a command that carries `--json` is compared structurally. `"..."` marks an open value. An object without `"...": "..."` is closed: exactly the keys shown.
- Plain text is checked only where a console block gives it. Otherwise only the exit code is required. This is why S-11 to S-13 assert only the exit code: their text output carries the caller's HOME path, which is not part of the contract.
- Errors go to stderr with exit 1, prefixed as shown in each assertion. There is no JSON error envelope on these paths (S-01).

## Output rules

- **Envelope.** Successful `--json` outputs of the shaping service are one JSON object. The unregistered-app refusal is plain text on stderr, not JSON (S-01, S-08).
- **Open vs closed.** Candidate and version payloads returned by `show`, `status` and `history` on a registered app are open: an implementation may add keys. The unregistered-app refusal is closed: exactly the line asserted in S-01 to S-08, because it must never leak a path, a cookie or another principal's data.
- **Errors** go to stderr with exit 1 (S-01 to S-13).

## Definitions (input)

- An **app** is a name registered on the host (for example by `bashy app add --type shaped`). Every verb in this contract takes the app as its first operand. A name that is not registered is refused before any candidate work (S-01 to S-08).
- A **candidate** is an isolated revision generated by `wish` or imported with `wish --from`; it is identified by a candidate id (`{ID}`) and never edits the app's active source in place.
- **Scope names** are exactly the set {`edit`, `shape`}: a scope name is valid when, lower-cased, it equals `edit` or `shape`, and invalid otherwise. Boundary pair: `bogus` is refused by the scope rule itself (S-09), while `edit` passes the scope rule and is then refused only because the app is not registered (S-10). `shape` includes `edit`. Audiences are circles AND (groups OR emails); an empty audience grants nothing.
- **Principals.** `--user` (alias `--principal`, or `BASHY_PRINCIPAL`) names the represented user; `--as` names the accountable caller; `--agent tool:model` names the generating agent. None of them overrides a remote console identity.
- The **wish request** is a plain-text request (see `examples/wish.txt`); the **scope grant** input is the flag form shown in `examples/scope-grant.txt`. No other input formats are part of this surface.

## Service rules

- `wish` generates a candidate in isolation; local `wish` waits for generation, and `wish --from WORKSPACE` copies a hand-made change without building in the supplied checkout.
- `verify` runs the trusted verifier on a candidate. Verification failure is a nonzero result with an inspectable verdict. `verify` does not call conform; conform evidence is produced only by `conform cert` and `conform mutate` (KI-4).
- `preview` shows a candidate in isolation: a URL on the paired console for a web app, the verified executable for a CLI-kind app, or a side-port URL for a service-kind app. Printing a preview URL is not evidence that a page rendered.
- `approve` re-verifies and then activates through the sealed activation gate. Only the owner approves. `reject` discards a candidate without activation.
- `undo` restores the previous version through the trusted gate; `restore` restores a named version through the same gate. Both are owner operations on the CLI (S-12, S-13 assert their refusal on an unfetched app).
- `history` lists the selected principal's versions. `status` shows the active version and candidates; `show` inspects one candidate; `diff` shows its patch.
- **Site MCP.** The mounted site MCP registers exactly the shaping tools `shape_wish`, `shape_pull`, `shape_push`, `shape_verify`, `shape_preview`, `shape_approve` and `shape_undo`. Verified members with `shape` scope can wish, verify and preview; a wish from a member without that scope becomes a request on the owner's queue without running an agent. Approve and undo remain owner-only. There is no MCP tool that restores a named version (KI-3). Account strangers and anonymous visitors cannot shape or file requests.
- **Group shaping evidence.** The group loop above (member wish, owner approval, a second candidate from an old base refused naming both revisions, pull/edit/push with replay refusal) is proven only in a sandbox with a stub agent and synthetic accounts (KI-1). App data across a change and a restore is not asserted anywhere in this contract (KI-2).

### S-01
Refuse `status` for an unregistered app, as plain text on stderr with exit 1.
```console
$ shape status no-such-app-xyz --user shape-tester
shape: app "no-such-app-xyz" is not registered...
```
exit: 1

### S-02

exit: 1

### S-09
Refuse a scope name outside the set {`edit`, `shape`} before any app work.
```console
$ shape scope set --app no-such-app-xyz bogus --circle c1 --json --user shape-tester
shape scope: unknown scope "bogus" (want edit or shape)...
```
exit: 1

### S-15

