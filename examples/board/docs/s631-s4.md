## No phone-home

`script/no-phone-home.sh` on the installed (pinned + patched) source
reports 189 hits, identical with the login PATH and with
`PATH=/usr/bin:/bin` (per the conductor's fail-open note on the
story). Every group is removed, off by default, or not shipped:

- Web analytics loader (Plausible, `apps/web/index.html`): removed by
  `board-shape.patch`; the loader only ran on vendor hostnames
  before, now the tag is gone entirely (shipped `index.html` has 0
  `plausible` hits, keeps 55 `/board/` refs).
- API vendor telemetry SDKs (`@sentry/node`,
  `@sentry/profiling-node`): absent from the shipped API bundle. The
  install bundles the API with esbuild aliasing both packages to
  `sentry-stub.ts` (no-op functions); the stub exports all 9 names the
  API uses (`init`, `captureException`, `captureCheckIn`,
  `addBreadcrumb`, `setUser`, `httpIntegration`,
  `nativeNodeFetchIntegration`, `nodeProfilingIntegration`,
  `withIsolationScope`). The wrapper never sets `SENTRY_*`, so the
  SDKs can never initialize. Remaining `sentry` strings in `api.mjs`
  are esbuild parser-grammar tokens (`clear_sentry`) and an LSP
  `telemetry/event` protocol string — inert, no endpoint.
- Web telemetry SDK (`@sentry/react`): still imported by the web
  bundle, but `apps/web/src/instrument.ts` skips `init` unless
  `VITE_SENTRY_DSN` is compiled in with a non-`KANEO_` value. The
  install never sets it, so the shipped bundle keeps the
  `KANEO_SENTRY_DSN` placeholder and initialization never runs. The
  only other `sentry.io` string in the shipped web bundle is an inert
  SDK warning message. `track()` in `track.ts` only fires when
  `window.plausible` is a function, which nothing defines after the
  loader removal (verified in the shipped `track-*.js` chunk).
- Cron check-ins and error-report calls (`captureCheckIn`,
  `captureException`, `addBreadcrumb`): inert without initialization;
  scheduler failures still log to the owner's own stderr
  (`data/api.log`).
- Update checks (`latest-version`, `api.github.com … /releases`):
  only in end-to-end tests and the marketing site's CLI install
  script (`apps/site/public/cli/install.sh|.ps1`). The shipped
  `api.mjs` does reference `https://api.github.com` — that is the
  owner-configured GitHub integration plugin (requires
  `GITHUB_APP_ID` + private key the owner provides), not an update
  check; it never fires without owner setup.
- Maintainer tooling (`scripts/provision-sentry-*.sh`,
  `sentry/*.json`, `renovate.json`, `.env.sample` comments, CI
  workflows, Dockerfiles, `pnpm-workspace.yaml` allow-list): not
  shipped. `packages/cli` test snapshots and `apps/site` privacy copy
  mention `sentry.io` as sample/task-view text or disclosure, not
  code paths in the app.
- Owner-configured integrations (chat webhooks, Git hosting, SMTP,
  billing, captcha): each takes owner-supplied secrets/URLs (Slack
  client takes a `webhookUrl` argument; GitHub needs owner env keys);
  off unless the owner sets them up, and traffic then goes only to
  endpoints the owner chose.
- No remote fonts or CDN scripts in the web app; no OTLP exporter in
  either shipped bundle (no `OTLP|otlp|localhost:431[78]` outside
  build-machine path strings).
- No bashy OTel added: the shipped artifact is a prebuilt
  third-party Node bundle, not our code — the correct scope is
  removal/stubbing/gating (done above), with scheduler failures kept
  on the owner's own stderr. Nothing in the wrapper points at a dhnt
  or vendor host.

Runtime: the candidate stack (`board-console`, node API, Postgres)
was run with an isolated data dir; every socket it held was loopback
(console `:22901`, node API listener, node→postgres, postgres
listener). No non-loopback connection from any of the three
processes during boot, migration, and page serve. No owner
integrations are configured in that data dir, so no outbound
integration traffic exists to log.
