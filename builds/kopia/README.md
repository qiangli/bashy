# kopia — bashy verified build

bashy runs the snapshot-backup repository server behind `bashy kopia` (Kopia)
only from a **bashy-CI-built, keylessly Sigstore-signed build of the official
upstream release tag**. This directory is the declaration for that build.
`fork/` is installed as the `bashy-build` branch of `github.com/qiangli/kopia`;
it carries no upstream source — the workflow checks out the upstream tag fresh
on every run.

## Build configuration, and how it differs from upstream

Upstream splits its release across two paths: the linux archives come from
`.goreleaser.yml`, and the macOS/Windows archives from the `Makefile`'s
`KOPIA_BUILD_FLAGS` targets.

| | upstream release | bashy build |
|---|---|---|
| `CGO_ENABLED` | `0` for the linux archives (`.goreleaser.yml` `env`); the macOS archives are built natively on a mac runner with cgo left at its default (`1`) | **same** (`GO_CGO` in `tool.env`) |
| `-trimpath` | **already used** (`KOPIA_BUILD_FLAGS`, and `flags:` in `.goreleaser.yml`) | same |
| `-ldflags` | `-s -w -X repo.BuildVersion=$(KOPIA_VERSION_NO_PREFIX) -X repo.BuildInfo=$(shell git rev-parse HEAD) -X repo.BuildGitHubRepo=$(GITHUB_REPOSITORY)` | `-s -w -buildid=` + the same three, with `BuildInfo` taken from `PIN`'s `UPSTREAM_COMMIT` instead of a `git` call |
| platforms | linux/freebsd/openbsd × amd64/arm/arm64 (goreleaser), macOS amd64/arm64/universal, windows/amd64 | the four bashy ships: linux amd64/arm64, darwin amd64/arm64 (see `../README.md` §Windows legs) |

Upstream already does the reproducible-build work here, so the only
substantive change is `-buildid=` plus a stamp that reads the pinned commit
from `PIN` rather than from `git`. `BuildVersion` drops the leading `v`, as
upstream's `KOPIA_VERSION_NO_PREFIX` does.

**No separate web-UI fetch.** Kopia's server UI is a normal Go module
dependency at this tag (`github.com/kopia/htmluibuild` in `go.mod`), so it
arrives through `go.sum` like everything else — no second, unpinned upstream to
download, and the SBOM covers it.

### Toolchain: an EOL-minor security override

v0.23.1's `go.mod` pins `toolchain go1.25.11`, and **Go 1.25 is no longer a
supported minor** now that 1.27 has shipped — Go fixes only its two newest
minors, so go1.25.11 is the last 1.25 release there will ever be. There is no
later patch to move to, and v0.23.1 is the current kopia release, so no
upstream tag carries a newer toolchain either. Staying on the tag's toolchain
therefore cannot be made safe at any patch level.

That is the one case `GO_TOOLCHAIN_SECURITY_OVERRIDE` may leave the upstream
minor, and then only to the **oldest supported minor's latest patch** — the
smallest language-version jump that gets security fixes again:

```
GO_TOOLCHAIN=1.25.11                    # what the tag's go.mod says
GO_TOOLCHAIN_SECURITY_OVERRIDE=1.26.9   # EOL-minor security override
```

The move clears every reachable stdlib finding on its own. What it leaves are
11 reachable findings in dependencies, all with published fixes, which
`GO_SECURITY_OVERRIDES` takes: `golang.org/x/net` v0.60.0,
`golang.org/x/crypto`, `google.golang.org/grpc` v1.83.1, `golang.org/x/text`
and the otel OTLP trace exporter v1.45.0. Taking the x/net and x/crypto fixes
into a graph this old moves 23 require lines by MVS and raises `go.mod`'s own
`go` directive from 1.25.8 to 1.26.0 (both releases declare it), so the
declaration names every module that moves — see `builds/README.md`
§`GO_SECURITY_OVERRIDES` — and the directive gate allows the rise only up to
the effective toolchain the override already sanctioned. The result is **zero**
reachable findings and an empty `vuln-ignore`.

Both halves retire themselves the moment a kopia tag ships on a supported Go.

## No tracking: every knob at v0.23.1

Kopia's one documented outbound call is its periodic GitHub release check, and
bashy turns it off with an **environment variable**, not a flag.

The flag looks tempting and does not work. At this tag
`--[no-]check-for-updates` is declared by the repository *connect* options
(`cli/command_repository_connect.go`), so it only parses after a subcommand
that installs them: negating it in the global position — before `server
start`, which is where a launcher naturally puts a privacy flag — is an
"unknown long flag" and kills the invocation. That is what made the no-egress
gate fail before this build. `KOPIA_CHECK_FOR_UPDATES` is the same switch read
from one place (`cli/update_check.go` consults it directly in
`maybeCheckForUpdates()`, and it is also the flag's own `Envar`), so it holds
for every invocation and every argv order.

`files/no-tracking.env` states the environment and global-flag policy used by
the headless launcher.

| Knob | Source | Upstream default | bashy |
|---|---|---|---|
| `KOPIA_CHECK_FOR_UPDATES` | [`cli/command_repository_connect.go` at v0.23.1](https://github.com/kopia/kopia/blob/v0.23.1/cli/command_repository_connect.go#L62-L74) | unset — updates **are** checked (a periodic GitHub release query) | **`false`** in `no-tracking.env`, so it applies to `repository create` and `server start` alike |
| `--no-persist-credentials` | [`cli/app.go` strategy at v0.23.1](https://github.com/kopia/kopia/blob/v0.23.1/cli/app.go#L234-L246) and [flag default](https://github.com/kopia/kopia/blob/v0.23.1/cli/app.go#L272-L281) | credentials are persisted; [Darwin selects macOS Keychain by default](https://github.com/kopia/kopia/blob/v0.23.1/cli/password_darwin.go) | passed globally to repository create and server start; `KOPIA_PASSWORD` supplies the password without persistence |
| `--otlp-trace` | upstream flag reference, <https://kopia.io/docs/reference/command-line/flags/> | off | **passed** as a global flag, before the subcommand; `otel.env` decides where the spans go |
| `--address` | `server start` | `127.0.0.1:51515` | `127.0.0.1:<port>` (stated) |
| `--insecure` / `--without-password` | `server start` | off | **on**: plain HTTP with no server-level auth, because the mesh is the boundary and the listener is loopback |

`files/no-tracking.env` also clears `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`
(Go's `net/http` honours them, so an operator shell could otherwise hand the
service an egress path) and pins `NO_PROXY` to loopback.

### OpenTelemetry

kopia is the one service in this set that **does** export. `--otlp-trace`
enables kopia's OTLP exporter through the standard SDK environment, so
`files/otel.env` leaves the SDK enabled and pins every destination at
`http://127.0.0.1:31415` — byte-for-byte the endpoints and protocols yoke's
`external/internal/serviceenv` `LocalOTLP()` installs. Metrics and logs have no
kopia exporter and are set to `none` rather than left to a default.

Because kopia legitimately dials the collector, the no-egress verdict tolerates
exactly two destinations: loopback to its own port, and `127.0.0.1:31415`.

### No-egress gate

`files/no-egress-test.sh` creates a filesystem repository and then starts the
built server bound to `127.0.0.1:15151` with `no-tracking.env` + `otel.env`,
probes `/`, `/api/v1/repo/status` and `/api/v1/sources` over loopback, idles
30 s, probes again and stops it. Both kopia invocations — `repository create`
and `server start` — run under the tracer with `--no-persist-credentials`, so
the update check cannot hide in the setup step and a headless macOS runner
never waits on Keychain. Any failure prints the complete repository-create and
server stdout/stderr logs before exiting.

- **Linux (authoritative):** a fresh network namespace (`sudo unshare --net`,
  only `lo`), traced with `strace -f -e
  trace=connect,sendto,sendmsg,sendmmsg` and run unprivileged via `setpriv`.
  Any AF_INET/AF_INET6 attempt other than loopback to its own port or to
  `127.0.0.1:31415` — including DNS and attempts the namespace makes fail — or
  a connect to a resolver socket fails the build.
- **macOS:** `sandbox-exec` denies all `network-outbound` except
  `localhost:15151` and `localhost:31415`, and denies the mDNSResponder socket;
  any Sandbox deny for the process in the unified log fails the build.

## Audit

The `audit` job runs the pinned `govulncheck` (`v1.9.0`) in source mode over
**the package the release builds** (`.`), with the same build tags and
build environment, and fails on any vulnerability that is **reachable** — one
whose first trace frame names a called function — unless it is listed with a
justification in `files/vuln-ignore` (empty today). Scoping it to the shipped
package is what makes "reachable" mean reachable *in the signed artifact*
(`builds/README.md` §What the audit judges). It then writes a CycloneDX SBOM
with the pinned `cyclonedx-gomod` (`v1.12.0`), generated with the same tags so
its component list is the artifact's too.

`govulncheck` and `cyclonedx-gomod` are themselves installed with a separately
pinned toolchain (`GO_AUDIT_TOOLCHAIN`, go1.27.2), independent of the one that
builds the binary: `govulncheck` v1.9.0 declares `go 1.26.0` in its own
`go.mod`, so coupling the two would make the audit fail to install on any tool
pinned to an older Go. The analysis itself still runs at this tool's effective
toolchain.

## Operator steps (not in bashy CI)

```sh
# in a clone of github.com/qiangli/kopia
git switch --orphan bashy-build
cp -R <bashy>/builds/kopia/fork/. .
git add .github/workflows/bashy-build.yml bashy-build
git commit -m "bashy-build: kopia v0.23.1 verified build"
git push -u origin bashy-build
git tag bashy-v0.23.1-1 && git push origin bashy-v0.23.1-1
```

Then repoint the yoke pin: `external/kopia`'s `Spec()` resolves `kopia/kopia`
from GitHub today (and `kopia.yaml` still says `version: v0.23.1`); it has to
become the signed fork release above, verified against the signing identity and
issuer in the table at the top.
