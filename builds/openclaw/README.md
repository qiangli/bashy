# OpenClaw gateway — bashy VERIFIED BUILD

bashy never starts a third-party-built service. This directory holds the
template the mirror fork needs to build the OpenClaw gateway from pinned
upstream source on fork CI, with tracking removed and OpenTelemetry pointed
only at the local collector. Each Linux arch ships TWO signed forms of the
same patched runtime: the **Dockerfile-built runtime tree** (`package/`
incl. `node_modules`), extracted from the pinned official upstream
Dockerfile's built `/app` and security-patched, AND a **distributable
gzip-compressed single-layer image tar** (`docker save` of the flattened
image piped through `gzip -n`, whose `/app`
is that exact patched tree — `docker load -i` it; Docker archive format, not
OCI layout) — the user host never touches the npm registry (see "What ships"
below).

## Where this runs (fork model)

The workflow does NOT live in bashy and NEVER runs here. The manager copies
the whole `fork/` tree as-is at the root of the mirror fork
(`github.com/qiangli/openclaw`) on a `bashy-build` branch:

- `fork/.github/workflows/bashy-build.yml` → the fork's build workflow
- `fork/bashy-build/` → runtime files the workflow needs (PIN, no-tracking
  env, OTel env, gateway config, no-egress gate, mock collector)

`fork/` is GENERATED by `../render.sh openclaw` (checked by `../check.sh`;
see `../README.md`) from the sources here: `tool.env` (the declaration,
shipped verbatim as `bashy-build/PIN`), `files/` (copied into
`bashy-build/` — incl. `Dockerfile.shipped`, the layered-image build,
`flatten-image.sh`, and `scripts/`), and the tool-specific workflow steps
`setup.yml` (Node + pnpm for the audit gates) and `build.yml` (frozen pnpm
install for the audit gates, audit gates, script unit tests, pinned upstream
Dockerfile build (unshipped base) + `/app` extract, SBOM of the extracted
tree, gate-first bundled-copy patch, re-stage of the exact shipped runtime,
layered-image build (never distributed), flatten + full-rootfs patch +
single-layer import, tarball + merged-`/app` + archive-layer
vulnerable-version gates, gzip-compressed docker-save image tar + digest per leg), which slot
into the shared skeleton `../_shared/bashy-build.yml` (pin → build → release
with sign, self-verify, attest, publish). Edit the sources, never `fork/`
by hand. Paths below that name `fork/bashy-build/X` come from `files/X`.

## Why the Dockerfile path (build 16 post-mortem)

Fork build 16 (run 38343035125) failed all four legs in runtime assembly:
the previous native path ran the upstream packager
(`scripts/package-openclaw-for-docker.mjs`) plus a generated npm lock and
`npm ci`, and the packager's staging runs an upstream script inside the
packed `runtime/package` tree, which lacks
`src/shared/non-packaged-plugin-dirs.ts`. The conductor directed the
simpler faithful path used now: build the pinned official `v2026.10.2`
upstream Dockerfile in CI — the Dockerfile's real final runtime, never a
reimplementation of its staging scripts — then extract its built `/app`,
security-patch the extracted tree, build the LAYERED image from the patched
tree (`Dockerfile.shipped`: FROM the base, COPY the patched tree over
`/app` — never distributed, since its lower layers still carry the base's
vulnerable copy), flatten its merged view to a SINGLE-LAYER image
(`flatten-image.sh`: export, full-rootfs patch incl. copies outside `/app`,
import with config parity), and sign/publish BOTH the extracted-tree
tarball AND a gzip-compressed `docker save` tar of the flattened image
(Docker archive format, `.docker.tar.gz`) for Linux amd64/arm64, gated over the distributed
archive layers. macOS
assets are deferred explicitly until a valid build path exists (macOS
runners have no Docker daemon, and the old native pack path is what died).
Nothing is pushed to any registry and no registry-built npm or ghcr
artifact ships: the images stay local to the legs that built them, and the
signed artifacts are the extracted `/app` tarball plus the `docker save`
tar of the shipped image (with its digest file binding image ID to tar
sha256).

Trigger: push of tags matching `bashy-v*` (e.g. `bashy-v2026.10.2-1`) on that
branch. No manual-dispatch trigger. The release is published ON THE FORK with
`GITHUB_TOKEN` (`contents: write`), signed keyless via cosign bundles
(`id-token: write`).

## Pinned upstream (`tool.env` → `fork/bashy-build/PIN`)

`openclaw/openclaw` tag `v2026.10.2`, commit
`b8952d477f0c932d8ddc6da5c89cab5a169b6ff1` (MIT licensed). The workflow checks
out `refs/tags/v2026.10.2` from upstream and FAILS unless `git rev-parse HEAD`
equals the pinned sha. PIN bumps are deliberate: only official stable release
tags are accepted — the workflow REFUSES `main`/dev branches, pre-releases
and RCs before checkout.

Toolchain (from the pinned `package.json`): `packageManager` pnpm@12.5.1
(corepack), `engines.node` >=24.16 <25 or >=26.1 — the workflow pins Node 24
and pnpm 12.5.1 to match.

## How to bump the pin

1. Review the upstream diff tag-to-tag (`openclaw/openclaw` compare view);
   pay attention to new network calls, new telemetry knobs, Dockerfile base
   image changes, and `packageManager`/lockfile changes.
2. Update `tool.env` (`UPSTREAM_TAG` + full `UPSTREAM_COMMIT`), run
   `../render.sh openclaw`, re-verify every
   knob table below against the new tag's docs/source, and update source
   lines.
3. The manager syncs the tree to the fork's `bashy-build` branch and cuts a
   release tag `bashy-v<upstream>-<n>` (e.g. `bashy-v2026.10.2-1`).

## Security patch (GHSA-ch52-4w7c-c8xp)

`http-cache-semantics` resolves to **4.2.0** at the PIN (via
`make-fetch-happen@16.0.1`). npm itself (12.x, a RUNTIME dependency of the
gateway) bundles its own copy at 4.2.0, and bundled dependencies ignore
overrides — so no workspace override can move the copy that ships (a global
override makes upstream's own `scripts/generate-npm-package-lock.mts`
validation fail the pack step: its broad rule charges the immutable bundled
copy against the range, `node_modules/npm/node_modules/http-cache-semantics
locked 4.2.0, expected >=4.3.0`). The control is therefore a
**runtime-tree security patch**, not a dev-only exception and not an audit
exception (see the `audit-exceptions` header, which deliberately does NOT
list it — an exception would wrongly imply the vulnerable version ships):

1. **Frozen pnpm install for the audit gates.** Each Linux runner first
   removes unused preinstalled Android, Haskell, .NET, and hosted toolchain
   files and prunes its Docker cache to make room for the pinned build. CI
   then installs `src/` with
   `pnpm install --frozen-lockfile --ignore-scripts` and runs the audit
   gates. This tree is the audit basis only — the shipped runtime is built
   by the pinned upstream Dockerfile in its own stages (step 2), never
   from this tree.
2. **Pinned Dockerfile build (UNSHIPPED base image).** Each Linux leg
   runs `docker build --file src/Dockerfile
   --build-arg OPENCLAW_EXTENSIONS="diagnostics-otel"
   --build-arg OPENCLAW_DOCKER_BUILD_NODE_OPTIONS="--max-old-space-size=4608"
   --build-arg OPENCLAW_DOCKER_BUILD_TSDOWN_MAX_OLD_SPACE_MB=4608` against the pinned
   source checkout, natively on its own arch, tagged
   `openclaw-gateway-base:<bashy-tag>`. The Dockerfile performs its own
   frozen pnpm installs, the `build:docker` + `ui:build` builds, and the
   production-deps merge into the final stage's `/app`. This base image is
   NEVER shipped, signed, or pushed — it still carries the vulnerable
   bundled copy below.
3. **`/app` extract + tarball (a signed artifact).** Each leg creates a
   container from its base image, copies out `/app` (`dist`,
   `node_modules`, manifests, skills/docs — exactly as the Dockerfile
   built it) to `installed/package` (keeping the long-standing `package/`
   top dir), and tars it to `out/<asset>-${GITHUB_REF_NAME}.tgz` (see
   "What ships").
4. **Bundled-copy patch, gate-first (shipped path).** BEFORE any signing,
   `--verify-only` decides: when the extracted tree is already clean the
   step is a loud no-op (`patch_bundled.py` itself REFUSES a silent no-op,
   so an unconditional call would fail a clean tree — fail-closed both
   ways); otherwise `fork/bashy-build/scripts/patch_bundled.py` replaces
   EVERY bundled `http-cache-semantics < 4.3.0` inside the extracted-tree
   tarball (in practice
   `package/node_modules/npm/node_modules/http-cache-semantics` when the
   tree carries an npm copy, covered by `test_patch_bundled.py`) with the
   registry `http-cache-semantics@4.3.0` tarball — verifying its registry
   `dist.integrity` sha512 (repo-pinned in `build.yml`, matching the
   upstream pnpm lockfile's 4.3.0 resolution) before use, fail closed on
   mismatch — repacks deterministically, asserts every other entry
   unchanged, and updates the CycloneDX SBOM component(s) for that package
   (version + purl) with a `bashy security patch GHSA-ch52-4w7c-c8xp` note.
   The SBOM is patched in place rather than regenerated because only the
   tarball is patched: the on-disk extracted tree still holds the pre-patch
   copy, so regenerating would reproduce the stale 4.2.0 entry.
5. **Re-stage the exact shipped runtime.** The (patched when needed)
   tarball is re-extracted over `installed/package`, so the on-disk tree
   IS the shipped bytes — the tree the shipped image is COPYed from next
   AND the tree the no-egress gate starts. Re-extract (never hand-sync),
   so drift is impossible.
6. **Layered-image build (patched `/app`, NEVER distributed).**
   `fork/bashy-build/Dockerfile.shipped` (`ARG BASE_IMAGE` /
   `FROM ${BASE_IMAGE}` / `COPY package/ /app/`, build context
   `installed/`) builds `openclaw-gateway-layered:<bashy-tag>` — the pinned
   base with the patched tree over `/app`, no network touched. Its lower
   layers still carry the base's vulnerable bundled copy, and `docker save`
   ships every layer, so this image is only the merge view the next step
   flattens — saving it would distribute the vulnerability.
7. **Merged-`/app` image gate.** `docker cp` copies `/app` back out of a
   fresh container from the LAYERED image; `diff -r installed/package
   image-app` proves the image's `/app` IS the shipped runtime, and
   `patch_bundled.py --verify-only` over the image-extracted tree FAILS
   the build if any `http-cache-semantics < 4.3.0` remains IN THE MERGED
   `/app`. The tarball gate (step 4's `--verify-only` re-run after the
   re-stage) enforces the same bound on the tarball. Both gates run before
   signing — but both see the MERGED view only, so neither can catch the
   lower-layer copy: that is the archive gate's job (step 9).
8. **Flatten + full-rootfs patch + import (the DISTRIBUTED image).**
   `fork/bashy-build/flatten-image.sh` exports the layered image's merged
   view (`docker create` + `docker export` — no code runs), then runs the
   new `patch_rootfs.py` over the WHOLE extracted rootfs, gate-first:
   loud no-op when clean, otherwise every bundled copy below 4.3.0 —
   INCLUDING copies OUTSIDE `/app` such as the Node base's own
   `/usr/local/lib/node_modules/npm/node_modules/http-cache-semantics` —
   is replaced with the integrity-checked 4.3.0 release (covered by
   `test_gate_image_archive.py`). The patched rootfs is re-tarred and
   `docker import`ed as single-layer `openclaw-gateway:<bashy-tag>`,
   re-applying the layered image's Entrypoint/Cmd/Env/User/WorkingDir/
   Labels read live from `docker inspect` (never hardcoded) and
   parity-checked afterwards. Known delta: `docker import` carries no
   HEALTHCHECK metadata — the gateway's `/healthz` `/readyz` endpoints are
   unchanged; orchestrators define their own probes.
9. **Docker-save + gzip + archive gate + digest.** `docker save` writes the
   FLATTENED image through deterministic gzip (`gzip -n`) to
   `out/<asset>-${GITHUB_REF_NAME}.docker.tar.gz`
   (`docker load -i` it — the distributable image; gzip-compressed Docker
   archive format, hence the extension, NOT an OCI layout). Compression is
   required: the single-layer save holds the whole rootfs (2.9 GiB
   uncompressed at the pin) and hard-fails the 2 GiB release-file limit
   uncompressed.
   `gate_image_archive.py --archive` opens the EXACT distributed `.gz`
   file — transparently decompressing it, so the scan covers the exact
   distributed content — and FAILS the build if ANY layer holds
   `http-cache-semantics < 4.3.0` anywhere in the filesystem; it refuses
   non-docker-save archives outright and FAILS archives at or above the
   2 GiB limit (`--max-bytes`). `out/<asset>-image.digest` binds the
   flattened image ID to the COMPRESSED tarball's sha256, plus compressed
   byte size and layer count. Self-checks before upload: the digest
   re-verifies, the image is exactly 1 layer, the compressed tarball is
   under the 2 GiB release-file limit (checked twice: the gate script's
   `--max-bytes` plus the shell `test`, both on the compressed bytes), and
   the distributed `.gz` file itself `docker load`s to the same image ID.
   Tarball, compressed image tar, and digest are all cosign-signed at
   release, so digest and signature bind the exact compressed bytes the
   gate checked.

(No workspace override is applied: npm-bundled copies ignore overrides,
and the dev-graph path is covered by the `audit-exceptions` BUILD-ENV
entry instead. The old pack-path helpers `write-npm-lock.mts`,
`apply-override.sh` and `assert-lockfile-diff.sh` are removed — the
Dockerfile path needs none of them.)

## Audit policy (braces GHSA-vfj7-8cjw-p6xm)

At v2026.10.2, `pnpm audit --prod --audit-level high` reports 0 high /
0 critical; `braces@3.0.3` appears only via dev tooling (lit-analyzer,
stylelint → fast-glob/micromatch → `micromatch@4.0.8 → braces@3.0.3` in
`pnpm-lock.yaml`). Narrow, reviewed exception — enforced by
`fork/bashy-build/scripts/audit-gate.mjs` against
`fork/bashy-build/audit-exceptions`:

- (a) `pnpm audit --prod --audit-level high` must exit 0; additionally the
  gate FAILS if `braces` appears in the `--prod` audit JSON at any severity.
- (b) On the full audit JSON, any high/critical advisory other than exactly
  the listed exception(s) FAILS.
- (c) An exception EXPIRES (fails the build) when its advisory now lists a
  patched/fixed version, or when its package appears in the `--prod` graph.
  An excepted advisory absent from the audit is a review note, not a failure.

The parser accepts npm v1 (`advisories`), npm v2+ (`vulnerabilities`), and
pnpm array shapes; anything else with non-empty content fails closed. The
full audit JSON ships per leg as a release asset
(`<asset>-audit-full.json`, e.g. `openclaw-gateway-linux-amd64-audit-full.json`;
per-leg names because all four legs upload `out/*` into one merged release),
plus the shared `audit-exceptions` file.

## No-egress gate (`no-egress-test.sh` + `mock-otlp-collector.py` + `scripts/no-egress-guard.mjs`)

Runs BEFORE signing in the workflow (the skeleton's `no-egress gate` step,
after ALL build steps), against the re-staged PATCHED tree
(`installed/package` — re-extracted from the patched tarball, COPYed into
the layered image, proven identical to the image's `/app` by the image
gate's `diff -r`, and carried byte-identical into the flattened image's
`/app`). So it starts the EXACT patched runtime that ships in both the
tarball and the image tar — and proves the shipped tree starts
with no registry access. The matrix is Linux-only, so the gate enforces on
every leg before signing (the script still exits 0 with a loud `SKIP` on
non-Linux hosts, which no longer occur in the matrix):

1. Positive control: a connect to an unroutable TEST-NET-1 address from
   inside `unshare -rn` (user + network namespace, loopback only) must FAIL —
   otherwise the sandbox proves nothing.
2. Starts the mock OTLP collector on 127.0.0.1:31415 (stands in for bashy's
   local collector) and the freshly built gateway in the same isolated
   namespace under `strace -e trace=%network`, with `OPENCLAW_CONFIG_PATH`
   exported.
3. Waits for `/healthz`, lets it run so startup and maintenance jobs would
   fire, then FAILS on any `connect()` to a non-loopback address.
4. Second layer: a `NODE_OPTIONS --import` guard hook wraps
   `fetch`/`http.request`/`https.request` in the gateway process, aborts any
   attempt at `registry.npmjs.org` / `telemetry.openclaw.ai`, and logs it —
   the log must stay empty. strace proves loopback-only; the hook names
   WHICH kill switch would have failed.

Defaults (`GATEWAY_ARGV=gateway`, health `http://127.0.0.1:18789/healthz`,
config `bashy-build/openclaw-bashy.json`) are overridable via env.

## What ships (patched runtime as tarball + single-layer image, per Linux arch)

Why the extracted tree: the Dockerfile's final stage already merges the
production install with the built `dist/` into `/app`, so extracting it
moves every dependency fetch inside the gates (audit, SBOM, patch,
no-egress) and the signed artifacts then run with no registry access —
the user host never runs `npm install`. No registry-built npm tree and no
ghcr image ships: all images are built locally on the leg from pinned
source and never pushed; what is published is the patched extracted-`/app`
tarball, the gzip-compressed `docker save` tar of the FLATTENED
single-layer image (`.docker.tar.gz` — compression is required: the
uncompressed save exceeds the 2 GiB release-file limit), and
the digest file binding them — all cosign-signed. The layered intermediate
images (`openclaw-gateway-base`, `openclaw-gateway-layered`) are never
saved, signed, or pushed: saving the layered image would distribute the
base's vulnerable copy in its lower layers.

Per-arch because native modules (if any) compile for their own arch: each
leg builds the Dockerfile natively, patches its own `/app` AND its full
rootfs, flattens to a single layer, and ships both forms on its own runner
(free GitHub runners only).

| Matrix asset | Runner | Signed runtime tarball | Signed image tar (docker-save) |
|---|---|---|---|
| `openclaw-gateway-linux-amd64` | `ubuntu-24.04` | `openclaw-gateway-linux-amd64-<tag>.tgz` | `openclaw-gateway-linux-amd64-<tag>.docker.tar.gz` |
| `openclaw-gateway-linux-arm64` | `ubuntu-24.04-arm` | `openclaw-gateway-linux-arm64-<tag>.tgz` | `openclaw-gateway-linux-arm64-<tag>.docker.tar.gz` |

macOS assets are DEFERRED explicitly until a valid build path exists
(macOS runners have no Docker daemon for this path, and the old native
pack path is what died in build 16).

Each tarball holds `package/` incl. `node_modules` (patched: no
`http-cache-semantics < 4.3.0` anywhere — see the security section). To run
one: unpack and run `node openclaw.mjs gateway` from `package/` — no
`npm install`, no registry access. Each image tar is the same patched
runtime as a loadable single-layer image: `docker load -i
openclaw-gateway-linux-<arch>-<tag>.docker.tar.gz`, then run
`openclaw-gateway:<tag>` (pick the tar matching your arch). Format note:
these files are gzip-compressed Docker archives
(`manifest.json` + layer tars), NOT OCI layout — `docker load` reads the
`.gz` directly (it sniffs the compression); a tar without `manifest.json`
fails the archive gate, as does any file at or above the 2 GiB limit.
Each leg also
publishes its own CycloneDX SBOM (`<asset>-sbom.cyclonedx.json`, scanned
from its extracted tree, then patched in place so it describes the shipped
tarball AND the flattened image's `/app` — same `/app` bytes; it does not
enumerate the base-OS files outside `/app`), its own full-audit
JSON (`<asset>-audit-full.json`), and its digest file
(`<asset>-image.digest`: the FLATTENED image ID plus the COMPRESSED image
tar's sha256, byte size, and layer count — verify with `sha256sum`
against the `.docker.tar.gz`, and with cosign below).
Shared by all legs: `openclaw-pin.txt`, `audit-exceptions`,
`SHA256SUMS`, plus one `.sigstore.json` keyless bundle per asset:

```sh
# any asset (tarball, image tar, digest, SBOM, audit JSON):
cosign verify-blob --bundle ASSET.sigstore.json \
  --certificate-identity \
    https://github.com/qiangli/openclaw/.github/workflows/bashy-build.yml@refs/tags/TAG \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ASSET
grep sha256: <asset>-image.digest  # compare against sha256sum of the .docker.tar.gz
```

## What is verified

- PIN tag is a plain `vX.Y.Z` release whose upstream GitHub release is
  neither draft nor pre-release; the bashy tag is `bashy-v2026.10.2-N`; the
  workflow refuses to run outside `qiangli/openclaw`; upstream checkout at
  `refs/tags/v2026.10.2` equals the pinned commit sha, the tag resolves to
  it, and the tree is pristine (shared `verify-pin.sh`).
- Frozen pnpm install for the audit gates: `pnpm install --frozen-lockfile
  --ignore-scripts` from the pinned lockfile (upstream is pnpm-based —
  `pnpm-lock.yaml`, `packageManager pnpm@12.5.1`; Node 24 matches the
  upstream Dockerfile `node:24-bookworm` base and the supported range in
  `openclaw.mjs`). Lifecycle scripts stay off. This tree is the audit
  basis only; the shipped runtime comes from the Dockerfile below.
- Pinned Dockerfile build per Linux arch (UNSHIPPED base): `docker build
  --file src/Dockerfile --build-arg OPENCLAW_EXTENSIONS="diagnostics-otel"`
  from the pinned checkout, natively per leg; the extracted tree must
  contain `node_modules`, `dist`, and `openclaw.mjs`. Nothing is pushed to
  a registry, and the base image is never signed.
- Audit gate: `pnpm audit --prod --audit-level high` clean, plus the full
  audit vs reviewed exceptions (`audit-gate.mjs`); per-leg
  `<asset>-audit-full.json` and shared `audit-exceptions` published as
  release assets. `http-cache-semantics` is patched, not excepted (see the
  security section above).
- CycloneDX SBOM per leg, scanned from its extracted tree and updated in
  place for the bundled patch so it describes the shipped tarball AND the
  flattened image's `/app` (same `/app` bytes; base-OS files outside `/app`
  are out of SBOM scope — see "What ships").
- Gate-first bundled-copy patch (`patch_bundled.py`) per leg: loud no-op
  when the tree is already clean (an unconditional patch would fail a
  clean tree — fail-closed both ways), otherwise every bundled copy is
  replaced with integrity-checked 4.3.0.
- Re-stage of the exact shipped runtime per leg: the patched tarball is
  re-extracted over `installed/package`, so disk, tarball, image, and
  no-egress target cannot drift apart.
- Layered-image build per leg (`Dockerfile.shipped`: FROM base, COPY the
  patched tree over `/app`; NEVER distributed), then the merged-`/app`
  image gate: `diff -r` proves the image's `/app` IS the shipped runtime,
  and `patch_bundled.py --verify-only` over the image-extracted tree proves
  the MERGED `/app` holds no `http-cache-semantics < 4.3.0`; the tarball
  gate proves the same for the tarball. All run before signing.
- Flatten + full-rootfs patch + single-layer import per leg
  (`flatten-image.sh` + `patch_rootfs.py`, gate-first incl. copies outside
  `/app`), with runtime config inherited from the layered image and
  parity-checked — then the archive gate (`gate_image_archive.py`) proves
  the DISTRIBUTED bytes hold no vulnerable copy in ANY layer, anywhere in
  the filesystem. Covered by `test_gate_image_archive.py`, which CI runs
  before anything it guards.
- Docker-save per leg: `docker save` of the flattened single-layer image
  piped through deterministic gzip to `<asset>-<tag>.docker.tar.gz`
  (gzip-compressed Docker archive format, not OCI layout)
  with `<asset>-image.digest` binding flattened image ID to compressed-tar
  sha256 (+ compressed bytes, layer count); digest re-verified, exactly 1
  layer enforced, compressed bytes under the 2 GiB release-file limit
  (gate `--max-bytes` plus shell `test`), and the distributed `.gz` file
  itself `docker load`ed to the same image ID before upload.
- No-egress gate (strace + in-process guard hook) passes on every leg
  before signing; it starts the gateway from the re-staged patched tree —
  the exact runtime that ships in both artifacts (same `/app` bytes).
- Every asset keylessly signed: `cosign sign-blob --bundle <asset>.sigstore.json`
  (cosign v3.1.3 via pinned installer), each bundle self-verified against
  the exact identity, AND `actions/attest` provenance over every asset in
  `SHA256SUMS` — identity is this workflow at the release tag, issuer
  `https://token.actions.githubusercontent.com`. Tarball, compressed image
  tar, and digest file are all signed, so the image's digest/identity
  verifies offline from the release assets.
- Release assets: two extracted-tree gateway tarballs + two gzip-compressed
  single-layer image tars (Linux amd64/arm64), two CycloneDX SBOMs, two full-audit
  JSONs, two image digests, `openclaw-pin.txt`, `audit-exceptions`,
  `SHA256SUMS`, plus one `.sigstore.json` bundle per asset. macOS assets
  deferred (see "What ships").
