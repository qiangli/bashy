USER REQUEST / OUTCOME
Enhance Bashy sprint management so managers periodically see host CPU, memory and disk pressure, diagnose which agents/workspaces/tests consume resources, receive actionable alerts, and take appropriate steps before the host or a vendor becomes overloaded. Include agent token/budget awareness for EVERY vendor involved and simple vendor-filtered checks under bashy models. This is the preventive follow-up to Sprint 138 P0 incident 33811caa1d10; the immediate CPU fix must ship first and must not wait for this broader enhancement.

1. HOST OBSERVABILITY AND DIAGNOSIS
Expose a compact resource status/diagnosis surface integrated with sprint status/show/tick and structured JSON. Suggested UX: bashy sprint resources [SPRINT] --json; diagnose and bounded watch/alert modes under the same surface. Report host capacity and normalized CPU utilization/load, memory available/pressure and swap where supported, filesystem free/used space and growth, sample window, timestamp and freshness. Attribute top consumers to process trees, agent identity, sprint, weave run/workspace, tests/builds and containers/VMs where observable; show unattributed consumption honestly. Include workspace, build cache and artifact sizes using bounded/cached scans. Surface stale/missing/unsupported observations explicitly; no platform silently reports healthy because metrics are unavailable. Reuse existing host, telemetry and process collectors.

2. PERIODIC CHECKS AND ALERTS
Perform configurable inexpensive checks while sprints run and before admitting expensive work. Use a shared host snapshot, bounded history, incremental reads, configurable warning/critical thresholds, sustained-pressure windows and hysteresis. Deduplicate alerts across managers and send compact changes to the accountable manager through existing inbox/tick channels; include resource, offender, severity, evidence and suggested action. Recovery must clear alerts. Monitoring must work while a manager is busy, preserve alerts across handoff, and must not recreate the P0 hot polling loop or dump full history into model context. No inference requests are needed merely to collect, threshold or refresh metrics.

3. ACTIONS AND LOAD PLANNING
Managers should proactively review/verify/merge submitted weave work, then prune eligible sprint-owned workspaces and reclaim derived artifacts. Reuse the existing review, merge, pause/resume and sprint/weave prune lifecycle. Report concrete reclaimable candidates and expected/actual bytes reclaimed; preserve dirty/unmerged work, source inputs, active workspaces and shared caches used by other builds. Dry-run actions should be reviewable; existing explicit cleanup authority can permit automatic execution. Under sustained CPU/memory pressure, reduce WIP, stagger heavy tests/builds, checkpoint and pause lower-priority owned work, then resume gradually when pressure clears. Do not kill other sprints' work or automatically merge unreviewed changes. Record each mitigation and outcome; coordinate host-wide limits so concurrent managers cannot all claim the same apparent headroom.

Discover registered remote test/build targets and assess reachability, spare capacity, toolchain/platform/data compatibility and existing user policy. When permitted, plan and schedule eligible jobs there and retrieve gate artifacts/results with host and revision provenance. No automatic provisioning/spending, data movement outside allowed boundaries, remote use without existing authorization, or pretending incompatible cross-platform runs satisfy a gate. When no permitted target exists, queue locally with an explanation. Test planning must include both local and remote load rather than simply relocating overload.

4. VENDOR, MODEL AND AGENT USAGE / BUDGET COMMANDS
Add an easily discoverable bashy models subcommand surface for status/usage, limits and budgets. Suggested CLI contract (document final consistent names): bashy models usage --all --json; bashy models usage --provider <vendor> [--model <name>] [--refresh]; bashy models limits --provider <vendor>; bashy models budget --provider <vendor>. Provide a --vendor alias if provider is canonical. Reporting commands are read-only; budget policy changes use an explicit mutation command. Group all providers used by active sprints, with per-account/profile, model, agent/run and sprint drill-down where attribution is available. Aggregate shared account quotas across agents, models and hosts where data is available so aliases do not falsely multiply capacity. Unknown external account consumption must remain an explicit limitation.

Show active concurrency, request/token rates, input/output/cached token usage as available, context headroom where observable, quota used/remaining, reset windows, Retry-After/rate limits, configured soft/hard token/spend/concurrency budgets, and spend/forecast when supported. Separate subscription allowance, metered API spend and local inference capacity; vendor quotas need not be token-denominated. Each value needs source, time/window and actual/estimated/unknown/stale classification. Never treat absent quota telemetry as zero usage or unlimited allowance. Cover every configured/active vendor with a status row, including unsupported/unavailable/authentication-required states. Use official supported APIs or documented local harness usage/status sources where available; protect credentials and avoid inference calls to probe budget. Unknown capabilities require clear adapter-specific limitations, not invented endpoints or spend accuracy. Reuse existing fleet headroom/billing/meter code; see Bashy story ae3218b21d9b on misleading cost estimates and 7e99fa9254fc on campaign management.

5. VENDOR-AWARE MANAGEMENT
Periodically refresh a shared cached view with bounded provider-specific cadence/timeouts/backoff; respect provider rate limits. Warn early about low quota, burn rate, budget exhaustion and vendor concentration. Before admitting more agents/tests using inference, enforce configured concurrency/token/spend constraints across all sprints; reserve capacity atomically where possible and release it on finish/crash. Pause/queue work or select an explicitly allowed suitable alternative with capacity; capability, authentication, privacy and billing constraints still apply. Do not overload one vendor because many aliases look like independent pools; do not create retry storms or silently spill from subscription to metered billing. Resource/budget decisions must be visible in sprint tick/continuity with concise reasons and recovery criteria. Policies configure thresholds, cadence, reserves, allowed vendors/targets and automatic-versus-manager actions.

COMBINED CONVENIENCE COMMAND — USER CONFIRMED
Use bashy sprint monitor as the primary manager-facing command combining system resources AND LLM services in one view. It composes the same collectors, cache, policy and provider adapters as the focused models commands; do not create a second monitor loop, second ledger, or contradictory metrics.

CLI CONTRACT
- bashy sprint monitor: bounded one-shot host-wide summary, including every active sprint and LLM provider in use. It must exit promptly and work without claiming a sprint lease or starting agents.
- bashy sprint monitor <sprint-id>: the same host-capacity and vendor-account context with the selected sprint's processes, agents, runs, token usage and budgets attributed where available. Never hide other sprints consuming the same capacity.
- --watch [--interval <duration>] [--duration <duration>]: explicit live monitoring, configurable bounded sampling cadence, cancellation and optional total duration. Interactive terminals get a compact refreshed view; non-TTY watch output is bounded incremental status/alerts rather than repeatedly printing full snapshots or history.
- --provider <vendor> (with --vendor alias), --model <name>, and --host <registered-target> allow focused diagnosis. Remote inspection follows discovery/access policy and never authorizes work dispatch or data transfer by itself.
- --json: versioned JSON snapshot with timestamps, sampling window, source/freshness/unknown markers, host metrics, provider/account limits and usage, sprint/run attribution, active alerts, and recommended actions. With --watch, emit documented NDJSON changes/alerts plus a bounded configurable heartbeat.

DISPLAY
Show host CPU/load, memory pressure/swap and disk headroom/growth; top responsible processes/runs and reclaimable workspace estimates; each involved vendor/account's availability, active requests/agents, tokens/rates, quota remaining and reset, budget/spend when supported; and a small prioritized list of alerts and proposed mitigations. Distinguish local inference host load from remote provider availability. Partial failures retain healthy sections with a clear degraded/unknown status for unavailable sections. Every finding should point to a specific run/workspace/provider and an existing focused inspect or action command where possible.

The default and watch forms are observational: no implicit pause, merge, prune, remote dispatch, model switching, quota acknowledgment or paid requests. Managers act through explicit existing lifecycle commands or already-authorized automation policy. The same summary/alerts feed sprint tick so live-monitor presence is not required for awareness. Preserve command usability outside a TTY and under concurrent managers.
