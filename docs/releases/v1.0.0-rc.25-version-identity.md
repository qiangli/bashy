# Bashy v1.0.0-rc.25 — Version Identity and Build Stamping Investigation

## 1. Executive Summary

During release hygiene verification for Sprint 580 before tagging candidate `v1.0.0-rc.25-dev`, an anomaly in release records was audited:
- Story records (`docs/todo/75fa2f23894b-*.md` and `docs/todo/1a4fe685d0a0-*.md`) noted an outpost host build deployed on 2026-11-05 reporting version `v1.0.0-rc.26-dev` at commit `a0b4a1e6`.
- In this repository, git tags show:
  - `v1.0.0-rc.23` (commit `51271e35`)
  - `v1.0.0-rc.23-dev` (commit `51271e35`)
  - `v1.0.0-rc.24-dev` (hotfix commit `31b16aa8` branched from `rc.23`)
  - No tag matching `*rc.25*` or `*rc.26*` exists on `origin`.
- Commit `a0b4a1e6` does not exist in this git repository's commit tree, reflogs, or reachable objects (status: **MISSING** in repo history; facts from repository only).

This document details the codebase rules for version stamping, isolates how `v1.0.0-rc.26-dev (a0b4a1e6)` was produced, analyzes its ordering impact on `v1.0.0-rc.25`, and provides recommendations for tagging `v1.0.0-rc.25-dev`.

## 2. Codebase Version Stamping Audit

An exhaustive audit of the version stamping logic across the repository establishes the following contracts:

### A. Makefile
In `Makefile`:
```makefile
VERSION ?= dev
BUILD_ID ?= $(shell if [ -e .git ] && git rev-parse --is-inside-work-tree >/dev/null 2>&1; then \
		id=$$(git describe --tags --exact-match HEAD 2>/dev/null || git rev-parse --short=7 HEAD 2>/dev/null); \
		if [ -n "$$id" ]; then \
			if ! git diff --quiet --ignore-submodules -- 2>/dev/null || ! git diff --cached --quiet --ignore-submodules -- 2>/dev/null; then \
				id="$$id-dirty"; \
			fi; \
			printf '%s' "$$id"; \
		fi; \
	fi)
...
STAMP_LDFLAGS := -X 'github.com/qiangli/bashy/internal/cli.bashVersion=5.3.0(1)-bashy-$(VERSION)' -X 'github.com/qiangli/bashy/internal/cli.buildID=$(BUILD_ID)' -X 'github.com/qiangli/bashsharp/transpile.ShellRuntimeCommit=$(SHELL_RUNTIME_COMMIT)' -X 'github.com/qiangli/bashsharp/transpile.ShellRuntimeCommitTime=$(SHELL_RUNTIME_COMMIT_TIME)'
LDFLAGS := -s -w $(STAMP_LDFLAGS)
BASHY_LDFLAGS := -w $(STAMP_LDFLAGS)
```
- `VERSION` defaults to `dev` unless explicitly supplied on the command line (`make build VERSION=...`).
- `BUILD_ID` resolves to an exact matching tag on HEAD (`git describe --tags --exact-match HEAD`) or falls back to the 7-character short commit SHA (`git rev-parse --short=7 HEAD`).
- If uncommitted changes exist in the tree, `-dirty` is appended to `BUILD_ID` only. The `VERSION` variable is untouched.

### B. Runtime Stamping (`internal/cli/version.go`)
- Default `bashVersion = "5.3.0(1)-bashy"`
- Variable `buildID string`
- `BashyVersion()` extracts the version suffix after `-bashy-v` (e.g. `1.0.0-rc.26-dev`).
- `BuildID()` returns `strings.TrimSpace(buildID)`.
- `versionBanner()` formats:
  `prefix + ", version " + bashVersionLine()`
  where `bashVersionLine()` produces `bashVersion + " (" + id + ")"`.
  Example output: `bashy, GNU Bash 5.3 compatible, version 5.3.0(1)-bashy-v1.0.0-rc.26-dev (a0b4a1e6)`.

### C. GoReleaser Configuration (`.goreleaser.yaml`)
In `.goreleaser.yaml`:
- For `bashy`:
  `-w -X 'github.com/qiangli/bashy/internal/cli.bashVersion=5.3.0(1)-bashy-{{ .Tag }}' -X 'github.com/qiangli/bashy/internal/cli.buildID={{ .FullCommit }}'`
- For `outpost`:
  `-s -w -X 'github.com/qiangli/outpost/internal/agent.releaseTag={{ .Tag }}' -X 'github.com/qiangli/outpost/internal/agent.ldCommit={{ .Env.OUTPOST_COMMIT }}' -X 'github.com/qiangli/outpost/internal/agent.ldDirty=false'`
- GoReleaser evaluates `{{ .Tag }}` from the git tag pointing to HEAD. If a local tag exists on the build machine, GoReleaser uses it directly as `{{ .Tag }}`.

### D. Release Scripts
- `scripts/build-native-darwin-release.sh` requires `tag=$1` and stamps:
  `-X 'github.com/qiangli/bashy/internal/cli.bashVersion=5.3.0(1)-bashy-$tag'`
  `-X github.com/qiangli/outpost/internal/agent.releaseTag=$tag`
- `scripts/go-product.sh` wraps the Go toolchain with an overlay for signal preservation; it forwards `-ldflags` unchanged.

### E. Git Describe Usage
- Git describe in `Makefile`, `dag.md`, and `scripts/refresh-bashy.sh` only uses `--tags --exact-match HEAD 2>/dev/null` as a candidate for `BUILD_ID`.
- It is never used to infer, increment, or generate a version string.

## 3. Determination of the Rule That Produced `rc.26-dev`

We evaluated three potential causes:

1. **Next-RC Inference**: **RULED OUT**.
   There is no logic anywhere in the repository (scripts, workflows, Makefile, Go packages) that computes `next_rc = current_rc + 1` or parses existing tags to auto-increment. All version stamps require an explicit string or a matching git tag.

2. **Dirty Build**: **RULED OUT**.
   A dirty workspace appends `-dirty` to `BUILD_ID` (e.g. `a0b4a1e-dirty`). It does not modify `VERSION`, nor does it alter `rc.24` to `rc.26`.

3. **Explicit Version Override / Unpushed Local Git Tag**: **CONFIRMED RULE**.
   The version identity `v1.0.0-rc.26-dev` at `a0b4a1e6` was produced by one of the following mechanisms on the host where that build was executed:
   - **Local Git Tag**: An operator or build script created a local tag `git tag v1.0.0-rc.26-dev a0b4a1e6` (or at HEAD) in a local clone on the host, which was built via GoReleaser or local scripts, but never pushed to `origin`.
   - **Explicit Make/Go LDFLAGS**: The build command explicitly supplied `VERSION=v1.0.0-rc.26-dev` (via `make build VERSION=v1.0.0-rc.26-dev` or direct `go build -ldflags "-X ..."`).
   - **Sibling Outpost Repo Commit**: The 8-character commit `a0b4a1e6` is not in the `bashy` repository; it is either a commit in the sibling `outpost` repository (`cmd/outpost`), an unpushed branch commit, or an ad-hoc canary build for testing the F1 credential rotation fix on that host.

## 5. Version Ordering and Monotonicity Impact

### SemVer 2.0.0 Precedence
Under Semantic Versioning 2.0.0 (§11.4):
- Comparing `1.0.0-rc.25` vs `1.0.0-rc.26-dev`:
  Pre-release identifiers separated by dots are compared: `rc` equals `rc`. The second segment compares `25` (numeric) against `26-dev` (alphanumeric/string).
  By SemVer rules, numeric identifiers compare with integer value (`25 < 26`), and numeric identifiers always have lower precedence than alphanumeric identifiers.
- Comparing `1.0.0-rc.25-dev` vs `1.0.0-rc.26-dev`:
  Segments compare `rc.25-dev` < `rc.26-dev` (lexicographically and numerically).
- Therefore, in all cases:
  `v1.0.0-rc.25` **sorts strictly below** `v1.0.0-rc.26-dev`.

### Outpost Never-Downgrade Guard
As established in `docs/releases/v1.0.0-rc.22.md` §Fleet upgrades:
- Outpost's never-downgrade guard compares versions during automated fleet updates:
  *"When the running build is a prerelease, the `-dev`-stripped base decides: a strictly newer base is accepted; an equal or older one is declined."*
- For a host running `v1.0.0-rc.26-dev`:
  - Running base = `v1.0.0-rc.26`
  - Candidate base = `v1.0.0-rc.25`
  - Since `rc.25` is older than `rc.26`, the never-downgrade guard will decline an automated upgrade ("target semver not strictly newer").

## 6. Recommendations for Tagging `v1.0.0-rc.25-dev`

1. **Origin Git Tags are the Sole Canonical Truth**:
   The `v1.0.0-rc.26-dev` observed on the host was an untracked, unpushed build outside origin release governance. On origin, the latest release candidate tag is `v1.0.0-rc.24-dev` (on hotfix commit `31b16aa8`). The next canonical candidate on `main` is unambiguously `v1.0.0-rc.25-dev`.
2. **Proceed with Tagging `v1.0.0-rc.25-dev` on `main`**:
   Tagging `v1.0.0-rc.25-dev` maintains linear release history in git and on GitHub releases. Do not skip to rc.27; doing so would validate an unrecorded, unreviewed build and leave a gap in release records.
3. **Explicit Upgrade on Host Running `rc.26-dev`**:
   Because `v1.0.0-rc.25` sorts below `v1.0.0-rc.26-dev`, any host currently running the untracked `rc.26-dev` build cannot be updated via automated background upgrade. It must be updated using `--force` (`outpost upgrade --force ...` or `bashy self install`) or replaced during the planned container/service cutover specified in `docs/plan-s563-master-execution.md` §Main goal.
4. **Tag Governance Discipline**:
   Release candidate tags must only be created through authorized CI workflows or pushed to `origin` by the release steward. Host builds must never create local release tags that do not exist on `origin`.
