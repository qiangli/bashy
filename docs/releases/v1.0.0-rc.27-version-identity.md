# Bashy v1.0.0-rc.27 — Version Identity and Build Stamping Investigation

## Decision (operator, 2026-11-06)

Option B is chosen: the candidate is **v1.0.0-rc.27-dev**, so it sorts above
the test host's unpublished `v1.0.0-rc.26-dev` build. `rc.25` and `rc.26` are
intentionally unused. The analysis below predates the decision and is kept as
history — it explains why `rc.25` was originally considered — and the operator
decision above supersedes the recommendation in section 6.

## 1. Executive Summary

During release hygiene verification for Sprint 580 before tagging candidate `v1.0.0-rc.25-dev`, an anomaly in release records was audited:
- Story records (`docs/todo/75fa2f23894b-*.md` and `docs/todo/1a4fe685d0a0-*.md`) noted a host build deployed on 2026-11-05 reporting version `v1.0.0-rc.26-dev` referencing commit `a0b4a1e6`.
- Verified facts gathered directly from the Windows test host (named solely by role):
  - Installed outpost binary reports:
    `outpost version v1.0.0-rc.26-dev`
  - Installed bashy binary reports:
    `5.3.0(1)-bashy-v1.0.0-rc.26-dev (83f5a5a176f3c9dd827bd4796d257090298890fc)`
- Exhaustive tree and history audit:
  - Neither `83f5a5a176f3c9dd827bd4796d257090298890fc` (`83f5a5a1`) nor `a0b4a1e6` exists anywhere in the commit history, reflogs, or tags of the local `bashy`, `outpost`, `yoke`, or `sh` repositories, nor do they exist on `origin` (status: **MISSING** from all canonical trees).
  - Canonical git tags on `origin` for `bashy` are:
    - `v1.0.0-rc.23` (commit `51271e35`)
    - `v1.0.0-rc.23-dev` (commit `51271e35`)
    - `v1.0.0-rc.24-dev` (hotfix commit `31b16aa8` branched from `rc.23`)
    - No tag matching `*rc.25*` or `*rc.26*` exists on `origin`.
- **Definitive Conclusion (replacing prior speculation)**:
  The `rc.26-dev` build did not originate from any automated next-RC logic or committed branch drift. It was built from an unpublished local tree with `VERSION`/tag set by hand or picked up by a local git tag during a GoReleaser run on that host.

This document formalizes the codebase rules for version stamping, isolates how this binary was produced, analyzes its ordering consequences on candidate `v1.0.0-rc.25-dev`, evaluates the two operator remediation paths, and provides a clear recommendation.

## 2. Codebase Version Stamping Audit

An exhaustive audit of the version stamping logic across the repository establishes the following contracts:

### A. Makefile Stamping
In `Makefile`:
```makefile
VERSION ?= dev
BUILD_ID ?= $(shell if [ -e .git ] && git rev-parse --is-inside-work-tree >/dev/null 2>&1; then \
		id=$$(git describe --tags --exact-match HEAD 2>/dev/null || git rev-parse --short=7 HEAD 2>/dev/null); \
		if [ -n "$$id" ]; then \
			if ! git diff --quiet --ignore-submodules -- 2>/dev/null || ! git diff --cached --quiet --ignore-submodules -- 2>/dev/null; then \
				id="$$id-dirty"; \
			fi; \
			printf '%s' "$$id"; \
		fi; \
	fi)
...
STAMP_LDFLAGS := -X 'github.com/qiangli/bashy/internal/cli.bashVersion=5.3.0(1)-bashy-$(VERSION)' -X 'github.com/qiangli/bashy/internal/cli.buildID=$(BUILD_ID)' -X 'github.com/qiangli/bashsharp/transpile.ShellRuntimeCommit=$(SHELL_RUNTIME_COMMIT)' -X 'github.com/qiangli/bashsharp/transpile.ShellRuntimeCommitTime=$(SHELL_RUNTIME_COMMIT_TIME)'
LDFLAGS := -s -w $(STAMP_LDFLAGS)
BASHY_LDFLAGS := -w $(STAMP_LDFLAGS)
```
- `VERSION` defaults to `dev` unless explicitly supplied on the command line (`make build VERSION=...`).
- `BUILD_ID` resolves to an exact matching tag on HEAD (`git describe --tags --exact-match HEAD`) or falls back to the 7-character short commit SHA (`git rev-parse --short=7 HEAD`).
- If uncommitted changes exist in the tree, `-dirty` is appended to `BUILD_ID` only. The `VERSION` variable is untouched.

### B. Runtime Stamping (`internal/cli/version.go`)
- Default `bashVersion = "5.3.0(1)-bashy"`
- Variable `buildID string`
- `BashyVersion()` extracts the version suffix after `-bashy-v` (e.g. `1.0.0-rc.26-dev`).
- `BuildID()` returns `strings.TrimSpace(buildID)`.
- `versionBanner()` formats:
  `prefix + ", version " + bashVersionLine()`
  where `bashVersionLine()` produces `bashVersion + " (" + id + ")"`.
  Example output: `bashy, GNU Bash 5.3 compatible, version 5.3.0(1)-bashy-v1.0.0-rc.26-dev (83f5a5a176f3c9dd827bd4796d257090298890fc)`.

### C. GoReleaser Configuration (`.goreleaser.yaml`)
In `.goreleaser.yaml`:
- For `bashy`:
  `-w -X 'github.com/qiangli/bashy/internal/cli.bashVersion=5.3.0(1)-bashy-{{ .Tag }}' -X 'github.com/qiangli/bashy/internal/cli.buildID={{ .FullCommit }}'`
- For `outpost`:
  `-s -w -X 'github.com/qiangli/outpost/internal/agent.releaseTag={{ .Tag }}' -X 'github.com/qiangli/outpost/internal/agent.ldCommit={{ .Env.OUTPOST_COMMIT }}' -X 'github.com/qiangli/outpost/internal/agent.ldDirty=false'`
- GoReleaser evaluates `{{ .Tag }}` from the git tag pointing to HEAD. If a local tag exists on the build machine, GoReleaser uses it directly as `{{ .Tag }}`.
- Notably, GoReleaser populates `buildID` with `{{ .FullCommit }}` (the full 40-character commit hash). The installed binary's banner `(83f5a5a176f3c9dd827bd4796d257090298890fc)` confirms that GoReleaser was run against an unpublished tree with commit `83f5a5a1...` tagged locally as `v1.0.0-rc.26-dev`.

### D. Release Scripts
- `scripts/build-native-darwin-release.sh` requires `tag=$1` and stamps:
  `-X 'github.com/qiangli/bashy/internal/cli.bashVersion=5.3.0(1)-bashy-$tag'`
  `-X github.com/qiangli/outpost/internal/agent.releaseTag=$tag`
- `scripts/go-product.sh` wraps the Go toolchain with an overlay for signal preservation; it forwards `-ldflags` unchanged.

### E. Git Describe Usage
- Git describe in `Makefile`, `dag.md`, and `scripts/refresh-bashy.sh` only uses `--tags --exact-match HEAD 2>/dev/null` as a candidate for `BUILD_ID`.
- It is never used to infer, increment, or generate a version string.

## 3. Determination of the Rule That Produced `rc.26-dev`

We evaluated three potential causes:

1. **Next-RC Inference**: **RULED OUT**.
   There is no logic anywhere in the repository (scripts, workflows, Makefile, Go packages) that computes `next_rc = current_rc + 1` or parses existing tags to auto-increment. All version stamps require an explicit string or a matching git tag.

2. **Dirty Build**: **RULED OUT**.
   A dirty workspace appends `-dirty` to `BUILD_ID` (e.g. `83f5a5a-dirty`). It does not modify `VERSION`, nor does it alter `rc.24` to `rc.26`.

3. **Unpublished Tree with Local Tag / Explicit VERSION**: **CONFIRMED RULE**.
   The version identity `v1.0.0-rc.26-dev (83f5a5a176f3c9dd827bd4796d257090298890fc)` was produced because:
   - The build occurred in an unpublished git tree containing commit `83f5a5a176f3c9dd827bd4796d257090298890fc` (not present on `origin` nor in local repos `bashy`, `outpost`, `yoke`, or `sh`).
   - A local git tag `v1.0.0-rc.26-dev` was created pointing to that commit, or `VERSION=v1.0.0-rc.26-dev` was explicitly passed during the build.
   - GoReleaser expanded `{{ .Tag }}` to `v1.0.0-rc.26-dev` and `{{ .FullCommit }}` to `83f5a5a176f3c9dd827bd4796d257090298890fc` for `bashy`, and set `releaseTag` to `v1.0.0-rc.26-dev` for `outpost`.

## 5. Version Ordering and Upgrade Impact

### SemVer 2.0.0 Precedence
Under Semantic Versioning 2.0.0 (§11.4):
- Comparing `1.0.0-rc.25-dev` vs `1.0.0-rc.26-dev`:
  Pre-release identifiers separated by dots are compared from left to right.
  Comparing numeric segment 2: `25` vs `26`.
  Numeric identifiers are compared with integer value (`25 < 26`).
- Comparing `1.0.0-rc.25` (final) vs `1.0.0-rc.26-dev`:
  Across distinct numeric pre-release identifiers, `1.0.0-rc.25` sorts strictly below `1.0.0-rc.26-dev`.
- **Consequence**:
  On that Windows test host, a candidate tagged `v1.0.0-rc.25-dev` **sorts strictly BELOW** the installed `rc.26-dev`.

### Outpost Never-Downgrade Guard & Upgrade Checks
As documented in `docs/releases/v1.0.0-rc.22.md` §Fleet upgrades:
- Outpost's never-downgrade guard compares versions during automated fleet updates and incoming release polls:
  *"When the running build is a prerelease, the `-dev`-stripped base decides: a strictly newer base is accepted; an equal or older one is declined."*
- Evaluating against the Windows test host:
  - Installed/running base: `v1.0.0-rc.26`
  - Candidate incoming base: `v1.0.0-rc.25`
  - Comparison: `v1.0.0-rc.25` is older than `v1.0.0-rc.26`.
- **Consequence**:
  Automated upgrade and incoming "newer release" checks running on that host will treat `rc.25` as older and decline the update ("target semver not strictly newer").

## 6. Operator Options and Recommendations

To resolve the discrepancy between the published canonical release series and the Windows test host, two options are available to the operator:

### Option A: Keep `rc.25` and Reinstall That Host Explicitly by Version
- **Action**:
  Proceed with tagging `v1.0.0-rc.25-dev` on `origin/main`. Reinstall or update the Windows test host explicitly by targeting the specific version (e.g. `outpost upgrade --force ...`, `bashy self install`, or via scheduled maintenance cutover).
- **Pros**:
  1. **Maintains Canonical Release Linearity**: Preserves a strict, contiguous git tag sequence on `origin` (`rc.23` → `rc.24-dev` → `rc.25-dev`).
  2. **Preserves Public Repository Integrity**: Does not bend public release numbering or skip release identifiers to cater to an untracked, uncommitted local experiment on a single test machine.
  3. **No Phantom Gaps**: Avoids leaving orphaned versions (`rc.25` and `rc.26` absent from GitHub releases and release ledgers).
- **Cons**:
  1. Requires explicit manual or scripted intervention (`--force` or reinstall) on that specific Windows test host to overwrite the installed `rc.26-dev` binary.

### Option B: Skip to `v1.0.0-rc.27-dev` for This Candidate
- **Action**:
  Skip `rc.25` and `rc.26` entirely; tag the next candidate on `main` as `v1.0.0-rc.27-dev`.
- **Pros**:
  1. **Automated Upgrade Compatibility**: Because `v1.0.0-rc.27-dev` sorts strictly higher than `v1.0.0-rc.26-dev` (`27 > 26`), Outpost's automated fleet upgrade and incoming release checks would accept the candidate without `--force` or manual intervention on the Windows test host.
- **Cons**:
  1. **Creates Gaps in Git and Release History**: Skips `rc.25` and `rc.26` on `origin` with no corresponding published release tags, commits, or artifacts.
  2. **Ratifies Ghost Builds**: Elevates an unpublished commit (`83f5a5a1...`) that does not exist in any canonical repository into a factor governing the public project release cycle.

---

### Recommendation: Option A (Keep `rc.25` and Reinstall Explicitly)

**Recommendation**: We recommend **Option A**.

**Reasons**:
1. **Source of Truth Discipline**: Git tags on `origin` must remain the single canonical source of truth for the project. The build on the Windows test host was an unpublished, unpushed artifact whose commit SHA (`83f5a5a176f3c9dd827bd4796d257090298890fc`) does not exist in any upstream repository. Public release versions must not be skipped due to unpushed local builds.
2. **Auditable Release Ledger**: The project's release documentation, sprint stories (e.g. Sprint 580 H1), and change ledgers explicitly anticipate `rc.25`. Skipping to `rc.27` would create confusion and audit discrepancies across documentation and tracking systems.
3. **Isolated Impact**: The version inversion affects only one internal test host (the Windows test host). Internal test hosts are intended for development validation and frequently receive targeted canary installations. Reinstalling or force-updating that host explicitly by version resolves the issue completely and safely returns the machine to the canonical release stream.
