# S503.6 macOS Python source-build dependency boundary

Scope: [native run 40218780251](https://github.com/qiangli/bashy/actions/runs/40218780251), the [independent receipt review](python-macos-source-40218780251/review.json), and the two retained `result.json` artifacts. This is an alternate Python.org **3.12.15** private-prefix source build on disposable `macos-15` and `macos-15-intel` runners. It is not the pinned 3.12.10 installer path or an operator-host installation. The following is an artifact-specific engineering review, not an approval to package or redistribute Python, Homebrew, or Apple binaries. `product_admitted=false` and `operator_admitted=false` remain unchanged.

## Exact observed linkage

The receipt review rehashed both artifact ZIPs and both `result.json` files, cross-checked 3,359 installed-file entries against 75 installed native files and the 78-entry Mach-O closure on each architecture, and found no change to the preinstalled system Python framework. I downloaded the same retained artifacts and independently rechecked each `result.json` SHA-256 against that review. `_lzma.cpython-312-darwin.so` has the following dynamic link to a **host Homebrew** `liblzma.5.dylib`:

The native receipts report successful `lzma` round trips. The Homebrew dylibs are outside the private Python prefix and do not appear among its inventoried installed files. The artifacts retained their paths, architectures and hashes, **not** copies of the dylib or a Homebrew bottle receipt. Thus this run proves dynamic use of those runner files, not byte-for-byte attribution of either file to a particular Homebrew bottle or proof that an operator has an equivalent copy.

The [XZ Utils v5.8.3 `COPYING`](https://github.com/tukaani-project/xz/blob/v5.8.3/COPYING) assigns **liblzma itself** to 0BSD. It assigns different terms to other parts of the source tree, including GPL-licensed scripts and some build files. The [historical Homebrew 5.8.3 formula](https://github.com/Homebrew/homebrew-core/blob/113d969515e8fa9bae8de1284971dea90cb08a05/Formula/x/xz.rb) likewise records the *whole formula* as `0BSD` plus `GPL-2.0-or-later`; that formula-wide expression does not make the linked liblzma dylib GPL. The [upstream 0BSD text](https://github.com/tukaani-project/xz/blob/v5.8.3/COPYING.0BSD) permits use and distribution. The closed conclusion is limited to the upstream **liblzma component's license classification**. If a final installer copies the Homebrew dylib, its exact bottle/source provenance, build inputs, file-level notices and redistributed bytes must be captured and reviewed; the formula and these CI path hashes alone do not establish that closure. An external-Homebrew route instead needs an explicit supported install/version/hash policy and operator-host proof.

## Apple operating-system libraries

Both closure receipts list these nine unresolved OS install names: `CoreFoundation`, `SystemConfiguration`, `libSystem.B`, `libbz2.1.0`, `libffi`, `libncurses.5.4`, `libpanel.5.4`, `libsqlite3`, and `libz.1` under `/System/Library` or `/usr/lib`. Their receipt entries have `shared_cache=true`, `sha256=null`, and `macos_shared_cache_license_review_required`; no Apple dylib bytes were retained or added to the inventoried Python prefix. [Apple Developer Technical Support](https://developer.apple.com/forums/thread/692383) describes the dyld shared cache as part of the macOS installation containing prelinked system libraries. Its details can change between OS versions. The narrow observed route is **dynamic use of the runner's OS libraries**, with no separately copied Apple system dylib demonstrated by this build. It does not assign a blanket open-source license to those libraries, certify their exact bytes, or authorize shipping copies of Apple's OS cache. [Apple's macOS license terms](https://www.apple.com/legal/sla/docs/macOSSequoia.pdf) and the actual product distribution channel remain relevant if packaging changes; no Apple-library redistribution decision is made here.

## Product decision still required

1. Choose whether Python and `liblzma` remain separately installed external dependencies or are included in a distributable. For an external route, pin and verify a supported 3.12.15 Python build and xz 5.8.3 library on real operator hosts, including the native architecture and actual linkage. The current 3.12.10 installer policy is a different artifact and must not be silently replaced by this research build.
2. For a bundled route, inventory final package bytes and transitive build/runtime inputs, preserve applicable Python/OpenSSL/xz notices, and review the actual copied Homebrew and Apple artifacts before admission. The present CI run retained only a private-prefix manifest and hashes; it did not upload a distributable.
3. Keep S503.6 open until the chosen path, all six native targets, and the rest of the transcription dependency closure are accepted. This review removes the mistaken inference that a whole-formula GPL expression necessarily applies to **liblzma**, while leaving final packaging and operator-host evidence open.
