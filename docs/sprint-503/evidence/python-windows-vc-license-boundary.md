## License and distribution disposition

The [Python.org release page](https://www.python.org/downloads/release/python-31210/) identifies the amd64 installer as recommended and arm64 installer as experimental. Its official [amd64 SPDX record](https://www.python.org/ftp/python/3.12.10/python-3.12.10-amd64.exe.spdx.json) and [arm64 SPDX record](https://www.python.org/ftp/python/3.12.10/python-3.12.10-arm64.exe.spdx.json) contain the matching installer SHA-256 values. I fetched and hashed the SPDX JSON: amd64 `1905207f988375b65dccbe3a1aafb22cc96b03f7826a4867c1b34006c214e571`, arm64 `09e90644e15ff7f4f337b8548a90b1e38060115f4ea7bdca330ad78a71e8fc33`. Each lists 34 packages, **zero file entries**, and no Microsoft/VC runtime package entry. Therefore those SBOMs do not establish the provenance or license terms of the four measured DLL files.

[Microsoft's redistribution guidance](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files) restricts redistribution of the VC runtime package and individual binaries to licensed Visual Studio users under the applicable Microsoft Software License Terms, and recommends central installation for servicing. The [architecture-specific redistributable URLs](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist) point to mutable latest releases; they are not immutable pins for the exact `14.51.36247.0` System32 files. The observed app-local VC files arrived in the Python.org installation target, but the retained artifact does not contain the installer payload manifest or DLL bytes to independently attribute them to a signed Microsoft source. PSF signing of the installer and Python's PSF license do not themselves grant Bashy a right to copy Microsoft's DLLs into a Bashy release. No such redistribution is proposed here.

An **externally installed** Python route could satisfy the package boundary without Bashy bundling a VC DLL: the operator separately obtains and installs the official Python.org interpreter and, where required, Microsoft's native VC prerequisite; Bashy only checks the chosen interpreter, installation-local and System32 paths, versions/signatures, and hashes. That is a route to review, not an admission verdict. A Bashy-managed download or install, a copied Python tree, a copied VC DLL, or an installer that embeds either package would cross a different distribution boundary. The [current external-runtime policy](../../../examples/transcribe/dependencies/windows-external-runtime.json) pins only two loaded names, and [all six admission entries](../../../examples/transcribe/dependencies/operator-python-admission.json) remain `unadmitted`.

To admit either Windows target, review a completed natural-load receipt and exact Authenticode results, resolve `vcruntime140_1.dll` and any further loaded VC imports, verify the actual native operator-host installation and offline replay, and choose a supported exact-version or signed-update policy for the System32 prerequisite. Then review the Python.org installer payload and its third-party notices against final package bytes. Neither this review nor a hosted runner receipt proves operator-host availability or grants Microsoft redistribution rights; `product_admitted=false` and `operator_admitted=false` remain in force.
